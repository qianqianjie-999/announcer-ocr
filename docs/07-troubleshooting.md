# 07 · 实战排障手册

按"现象 → 处置"组织，全部条目来自真实踩坑（附日期），现场先查本文。

## 帧采集

### 摄像头打开失败 / 取帧失败刷屏
- `ls /dev/video*` 确认设备在；USB 摄像头换一个 USB 口重插（UVC 控制超时
  换口即恢复，2026-10-07）
- `fuser -v /dev/video0` 查占用：常见凶手是上次**非正常退出**留下的孤儿 ffmpeg
  和 pipewire 抢占，清理后重启
  > 2026-10-11 起程序自己处理 SIGTERM/SIGINT：收到信号会先播完队列、再收掉
  > ffmpeg 子进程才退出（`src/signal.rs` + `PipeGrabber::drop`）。所以
  > `systemctl restart`、`Ctrl+C`、`kill <pid>` 都不会再留孤儿。
  > 只有 `kill -9` / 掉电这类"来不及执行析构"的情况才会复现本条。
- 启动期失败会快速报错退出（配置错误应立刻暴露）；**运行中断流会自动重启
  ffmpeg**，只有持续失败才刷日志——看到刷屏说明设备真的没了

### ps 里挂着 defunct 僵尸 ffmpeg
已修复（kill+wait 收尸）。若再现，检查 capture.rs 收尸代码是否被改动。

## 检测与识别

### 换屏了但不触发 OCR
1. 看 `_live/` 有无新触发帧——没有则是检测层问题：`changed_ratio` 调小
2. 触发帧里画面正常但仍不触发：确认 ROI 是否盖全屏面（ROI 收太紧会裁掉号码）
3. 摄像头自动曝光剧烈漂移场景：亮度对齐已兜底，若仍漏检调大 `diff_threshold`
   容忍度或检查固定曝光可能

### 识别结果全乱码
- 检查是否走了增强图（红通道+Otsu）——原图直喂 psm11 实测全乱码
- `tesseract --list-langs` 确认 `chi_sim` 在；无包时 `TESSDATA_PREFIX` 指向自备
  tessdata 目录（本地开发机常见坑，2026-10-07）
- ROI 里混入背景杂物：标定收紧 ROI，实测全画幅模式下识别文本"满屏噪声"

### 同一号码重复播报
查日志 CSV 原始文本列，常见两类：
- `C01`→`CO01` 形近误读：已由 `fold_window_zeros` 修复（C001→C01）
- 其他新变体：**先给 ocr.rs 补失败测试用例，再改清洗规则**，防止回归

### 窗口号丢了字母（`GA777,03`）
正则分支 2 允许无字母窗口（纯数字窗口是合法场景），属召回/精度权衡。
若现场窗口必有字母前缀，可在 config 的 pattern 里收紧 `{0,2}`→`{1,2}`。

### 切到主码流后一个号都读不出（2026-10-22）
**现象**：同一张图，手动 `tesseract --psm 6` 完美读出"请GA166到C04号窗口办理"，
服务却一路 INVALID。
**原因**：`--psm 11`（稀疏文本）是为**单行窄条**调的；主码流下 ROI 变成覆盖三行的
大区块后，psm 11 彻底失效（读成 `Al4smpx和D` 这类垃圾）。
**处置**：改 `ocr.psm` 为 **6**（整块文本）。切码流时这一项必须同步改，
否则现象极具迷惑性——存证帧人眼完全清晰，只有服务读不出。

### 屏幕有号、OCR 也读得出，但永远不播报（2026-10-22，已代码修复）
**现象**：存证帧和临时图都能读出号，日志里却没有一条 `[播报]`，也没有闸门拦截记录，
服务看着"活着"却持续静默（现场 16:14~16:54 整整 40 分钟）。
**原因**：两个机制撞车——
1. 过曝帧下 tesseract 是 **0.1s 正常退出 + 空输出**（不报错、不算失败），
   被当成"没号"，`empty_streak` 一路涨到 4 → 兜底间隔被退避拉到 **30s**；
2. 每轮 OCR 开头会先清候选：`confirm.retain(|_, v| now - v.1 <= ttl_eff)`，
   而当时的 `ttl_eff` 只有 **4s**（旧算法只覆盖 OCR 耗时，过曝帧耗时几乎为 0）。
   **间隔 30s > TTL 4s → 计数每轮被清零 → 永远凑不齐要求的确认次数**。
**处置**（二选一，代码已治本）：
- 升级到含 `effective_ttl()` 的版本：TTL 自动取
  `max(配置值, 3×OCR耗时, 1.5×本轮等待, 1.5×下轮等待)`，退避拉到 30s
  时 TTL 自动抬到 45s，死锁不再可能；
- 老版本应急：把 `detect.confirm_ttl_sec` 从 4 改到 **40**（必须 > 退避上限 30），
  并把 `static_fb_sec` 10 → 3 加速静帧确认轮。
**注意**：这个 bug **与码流无关**。辅码流在暗光/条纹期读对率下降时同样会踩
（今晨暗光识别率 82% 已在临界），触发条件是"连续 ≥4 轮空读 + 画面静止只能靠兜底轮"。

### 画面看着清晰，OCR 却全空（2026-10-22）
**原因**：摄像头自动曝光把画面拉得过亮，浅蓝底白字**对比度崩塌**，
二值化时字和底融成一片。人眼看着清楚，OCR 读不出——和暗光条纹是同一个病根
（曝光随环境光波动）。
**处置**：摄像头开 **50Hz 防频闪**（大华 CGI，Digest 认证）：
```
configManager.cgi?action=setConfig&VideoInOptions[0].AntiFlicker=1
```
开启后快门被钳制在 1/100s，过曝和条纹一起治掉，实测多帧立刻恢复读出。

## 播报与语音

### 该播不播 / 播报堆积
- 去重集**每天本地零点自动清理**（`announced_ttl_sec: 0`，2026-10-11 起）；
  程序重启也会立即清空。两种情况屏上号码都会重播一次——预期行为，不是 bug
- 若发现"整天某个号码只播一次、之后再也不出声"，先看 journal 里有没有
  `[维护] 去重表清理` 行：没有说明 `announced_ttl_sec` 被配成了负数（永不清理）
- 播报线程队列有深度上限，密集换屏会丢最旧——现场属合理降级

### espeak 读英文/音质差
espeak 对拉丁字母**设计上按英语读**。中文场景：换 piper + `spell_number: true`
（详见 05-tts.md）。

### piper 首条播报特别慢（十几秒）
CLI 模式每次重载 onnx 模型。部署常驻合成服务（`piper_url`），挂了会自动回退。

### 无 root 装运行时
espeak-ng：`apt download` + `dpkg -x` 解包到用户目录 + 环境变量注入（05-tts.md）。
piper：目标机 python 重建 venv（**3.11 的 venv 在 3.12 不可用**），模型文件可复用。

## 程序与系统

### 重复启动直接退出
单实例锁（回环端口 51888 占用）。要跑第二实例改 `lock_port`。

### 优雅停机与重启（2026-10-11 新增）
程序现在自己处理 `SIGTERM`/`SIGINT`（`src/signal.rs`），退出顺序是：

1. 主循环看到停止标志 → 跳出循环（不再读新帧）
2. 等播报队列播完（有界 10s，避免把已确认的叫号掐掉）
3. `PipeGrabber::drop` 收掉 ffmpeg 子进程（kill + wait，不留孤儿）

所以 `systemctl restart`、配置台"一键保存"、`Ctrl+C`、`kill <pid>` 都是安全的；
退出码 0，systemd 记为 `Result=success`。只有 `kill -9` / 掉电来不及走析构。
journal 里对应的三行留痕：`[退出] 收到停止信号…` → `[退出] 已优雅停机`。

### 日志写满 / 磁盘增长
- 程序侧：`log_max_mb`（默认 8）触发即把 `announce_log.csv` 归档到
  `logs_archive/announce_log_<时间戳>.csv`，只留最近 `log_keep`（默认 6）个
- 部署侧：`announce-cleanup.timer` 每天 03:30 兜底（归档、7 天前的存证图、
  陈旧 `req`/`.tmp`、journal 收缩、磁盘 <500MB 激进清理）
- 两侧归档命名一致，可共存；把 `log_max_mb` 设 0 即完全交回部署层

### 启动时清理 `_live/`
启动只删 `latest.jpg.tmp` 与 `req`（上次 kill -9 / 掉电的半成品）。
**不删 `trig_*.jpg`**——那是上一轮的现场证据，排障时最需要它；保留期由部署层按 7 天管理。

### 日志文件没内容/报写入失败
文件被 Excel 等占用时重试 3 次后丢弃该条（主流程不受影响）——关掉占用者即可。
抓帧日志每 10 分钟才一条（降噪设计），不是卡死。

### OCR 期间系统卡顿
确认 `OMP_THREAD_LIMIT=1`：tesseract 默认开满核并行，会饿死主循环的帧差检测，
单线程反而整体更快（靶机实测）。

## 码流切换与 RTSP 并发（2026-10-22 现场）

### 主码流只允许 1 路并发
大华摄像头主码流会话数有限：服务已占 1 路时，第二路 ffmpeg 直接 **0 帧**抢不到。
**调试期间禁止再开第二路 RTSP**（含手动 `ffmpeg -frames:v 1` 抓图、盯屏哨兵脚本）。

更隐蔽的坑：短连接抓图会抢占并**打断服务的长连接 GOP**，服务侧收到半帧/蓝屏，
出现"哨兵读得出、服务读不出"的假象，极易把排查带偏。
要看画面只能走内部通道：

- 服务自己存的存证帧 `/opt/announce-rs/_live/trig_*.jpg`
- 截获服务喂给 OCR 的临时图 `/tmp/announce_rs_ocr.*.png`

### 切主码流要同步改的参数（漏一项就翻车）

| 项 | 辅码流 | 主码流 1080p |
|---|---|---|
| `camera_source` subtype | 1 | 0 |
| `roi` | 单行小框 | **必须重新标定**（实测 `[1080,369,570,69]`） |
| `rows` / 行距 | 1 / — | 3 / **`row_pitch_ratio: 1.0`**（等价绝对像素 70） |
| `ocr.psm` | 11 | **6** |
| 摄像头编码 | — | 建议 1920×1080 H.264 15fps |

> **行距用 `row_pitch_ratio` 而不是 `row_pitch`**：实测行距≈行高（主码流行高 69、行距 70），
> 用相对值换任何分辨率都不用重算。若坚持用绝对像素，主码流 1080p 画布下填 **70**。
> ⚠️ 千万别沿用辅码流那个按比例换算出来的 137——它源自辅码流的 73，而 73 本身就是错的
> （辅码流 704×576 画布下真实行距约 37，等于行高）；只是辅码流 `rows=1` 从未启用多行，
> 这个错误值一直没被检验，切主码流时按比例一放大就崩了。

> 原 2560×1440 H.265@25fps 软解要 **333% CPU**；改成 1080p H.264@15fps 降到 **54%**。
> 长跑资源实测（i3-7100 / 3.8G 内存）：ffmpeg 57.6% CPU、RSS 230MB，19 分钟仅 +0.9MB，
> 温度 39~45°C、swap 0 —— **主码流不会因资源死机**。

标定行距的正确做法：抓一帧转灰度做**行投影**找文字段边界（实测第 1 行 383~410、
第 2 行 452~479 → 中心距 70），别靠目测——目测写成 137 会让第 2/3 行切到行间空隙。

### 主码流实测配置（2026-10-22，1920×1080 画布，可直接抄）

```jsonc
"camera_source": "rtsp://admin:pass@192.168.31.2:554/cam/realmonitor?channel=1&subtype=0",
"capture_width": 1920, "capture_height": 1080,
"roi": [1080, 369, 570, 69],
"detect": {
  "rows": 3,
  "row_pitch_ratio": 1.0,     // 等价 row_pitch=70；用相对值，换分辨率不用重算
  "confirm_ttl_sec": 4.0      // 新版本已自动覆盖退避间隔，无需改 40
},
"ocr": { "psm": 6 }            // 主码流三行区块必须 6，psm 11 全废
```

### Web 配置台会回写覆盖 config.json（2026-10-22 踩坑）
`config_web.py` 常驻进程用**内存里的旧配置**回写文件。命令行 `sed` 改完配置、
重启服务后，配置台一动就把 psm / row_pitch / TTL 全滚回旧值（当天连踩三次）。
**正确顺序**：先停配置台 → 改 config.json → 重启 announce-rs → 最后再起配置台。

## 现场部署核对单（2026-10-07 据现场照片整理）

到场后按此逐条核对，多为环境适配而非程序问题：

### 滚动字幕跑马灯
竖屏机下半部有滚动字幕区，字幕滚动会让帧差**持续触发 OCR 白烧 CPU**。
标定 ROI 时只框上半"当前办理"两行，把滚动区排除在外。

### 玻璃反光（屏面倒影清晰可见）
反光文字会污染 OCR / 产生假候选。摄像头**避开正对反射角、偏角度安装**；
若反光区域固定且在 ROI 外则无影响。

### 双屏同框（旁边另有事项清单屏）
摄像头视野可能同时框到两块屏。ROI 必须只框叫号机，标定后用
`_live/` 存证帧检查框内无杂物。

### 竖屏两行布局
与测试卡（两卡并排）布局不同，psm11 两种都适配；但 ROI 宽高比不同，
**到现场后用 Web 配置台重新拖框标定一次**（保存后重启服务生效）。

### 号码格式核对
现场实测：号码 `GA204`/`GA200`（2字母+3位数字）、窗口 `C06`/`C08`。
config 现有 pattern `\d{3,4}` 口径已覆盖，无需改动；若换现场先确认位数。

## RTSP 摄像头接入（2026-10-07 端到端实测）

最终部署用 RTSP 网络摄像头，切换只改一处配置：
`"camera_source": "rtsp://user:pass@摄像头IP:554/stream1"`（或 Web 台编辑，
自带双重校验）。实测 `mediamtx → ffmpeg TCP → 帧差/OCR` 全链路通过。

### 接入核对单
- **RTSP 地址**：摄像头后台确认（常见 `rtsp://user:pass@IP:554/stream1`），
  debian 与摄像头同网段可达：`ffprobe -rtsp_transport tcp -i <url>` 能列出流即通
- **用子码流**：640×360 足够叫号屏 OCR，带宽/解码减负；
  `capture_width/height` 改成与子码流一致（如 640×360）
- **ROI 重新标定**：分辨率变了旧 ROI 可能出界——出界时程序跳帧并告警
  `[警告] ROI ... 超出帧`（只告警一次，不再 panic），改好 ROI 即恢复
- **强制 TCP**：代码已固定 `-rtsp_transport tcp`，UDP 花屏帧不进 OCR；
  摄像头端如限制传输协议请放开 TCP interleaved
- **断流自愈同样适用**：网络抖动断流 → 3s 自动重拉（与 USB 同一机制）
